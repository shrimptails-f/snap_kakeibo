# デザインガイドライン

## 1. デザイン原則

snap_kakeibo は「レシートを取り込み、確認し、必要な箇所だけ直す」ための家計簿である。装飾よりも、金額と解析状態を迷わず理解できることを優先する。

1. **入力を少なくする**: AI 読み取り結果を起点にし、利用者には確認と修正を求める
2. **状態を隠さない**: アップロード、解析、登録、失敗の現在地と次の操作を示す
3. **金額を比較しやすくする**: 計上額を主、読取金額と調整額を補助として一貫して表示する
4. **モバイルを優先する**: レシート撮影直後のスマートフォン操作を基本にする
5. **回復手段を示す**: エラーだけで終わらず、再解析、再アップロード、戻る操作を案内する

## 2. ビジュアル方針

白を背景に、落ち着いた緑を主要色として使う。UIの緑は主要操作、登録完了、選択状態など「進める・できた」ことに限定し、装飾目的で多用しない。注意(warning)は橙色、失敗(danger)は赤で、いずれも一般的な意味に合わせる。

通常テキストと白背景の組み合わせは WCAG AA(4.5:1)を満たす値にする。`--color-primary` の白文字は 6.4:1、`--color-warning` の白文字は 5.2:1、`--color-text-muted` は白と `--color-surface-subtle` のどちらでも 4.5:1 以上。

### カテゴリの共通色

カテゴリの保存値と表示名は [ユビキタス言語](../../docs/ddd/ubiquitous-language.md#カテゴリ) に従う。全画面のグラフ・凡例・カテゴリ表示では、次の固定の対応を使う。カテゴリ色は分類を示すための色で、成功・失敗などの状態色とは役割を分ける。

| 保存値 | 表示名 | CSSトークン | 色 |
| --- | --- | --- | --- |
| `food` | 食費 | `--color-category-food` | `#39795a` |
| `daily_goods` | 日用品 | `--color-category-daily-goods` | `#4f80ad` |
| `medical` | 医療 | `--color-category-medical` | `#b45664` |
| `transport` | 交通 | `--color-category-transport` | `#39878b` |
| `utilities` | 水道・光熱・通信 | `--color-category-utilities` | `#827c35` |
| `entertainment` | 娯楽 | `--color-category-entertainment` | `#7159a6` |
| `social` | 交際・会食 | `--color-category-social` | `#b87830` |
| `clothing` | 衣類 | `--color-category-clothing` | `#a75587` |
| `education` | 教育 | `--color-category-education` | `#4d6494` |
| `other` | その他 | `--color-category-other` | `#8e699f` |
| `unknown` | 分類不能 | `--color-category-unknown` | `#7b858d` |

```css
:root {
  --color-category-food: #39795a;
  --color-category-daily-goods: #4f80ad;
  --color-category-medical: #b45664;
  --color-category-transport: #39878b;
  --color-category-utilities: #827c35;
  --color-category-entertainment: #7159a6;
  --color-category-social: #b87830;
  --color-category-clothing: #a75587;
  --color-category-education: #4d6494;
  --color-category-other: #8e699f;
  --color-category-unknown: #7b858d;
}
```

- カテゴリIDをキーに参照する。表示順・金額順・月・画面が変わっても色を変えず、配列の添字で割り当てない。
- 本実装では共通トークンとカテゴリIDの対応を共有し、画面固有CSSへ色値を複製しない。独立したHTMLモックも本表の名前と値に揃える。
- 凡例と積み上げ順は上表の定義順に固定する。内訳一覧を金額順に並べ替えても色の対応は維持する。
- 色だけで識別させない。カテゴリ名・金額を凡例、ツールチップ、テキスト一覧でも表示する。`other`（その他）と `unknown`（分類不能）は別カテゴリとして扱う。
- 色は棒・円グラフ・小さな色見本に使い、本文と金額は `--color-text` で表示する。色付き背景の上に白文字を一律に載せない。隣接部分に境界線を入れ、必要ならパターンを併用する。
- ホバーとキーボードフォーカスで対象月・カテゴリ名・金額を表示し、タップでも同じ情報を確認できるようにする。ツールチップ上へポインターを移しても消さず、Escapeで閉じられるようにする。
- 小さい区画をタップできない場合に備え、44px以上の月選択操作から同じ月の内訳一覧へ切り替えられるようにする。
- 積み上げの高さは `category_totals` の明細合計。`total_recorded_amount` の計上額と一致するとは限らないため、表示切替・見出し・説明で区別する。差額を架空のカテゴリに割り当てない。

## 3. タイポグラフィ

- 日本語を読みやすい system font stack を基本とし、Web Font は性能と配信方針を決めてから導入する
- 本文はモバイルで `16px`、補助情報は `14px` を下限の目安とする
- 本文の行高は `1.6`、見出しは `1.3` 前後とする
- 金額には tabular numbers を使い、桁を比較しやすくする
- 大見出しの連続より、ラベルと値の明確な階層を作る

```css
.amount {
  font-variant-numeric: tabular-nums;
}
```

## 4. レイアウト

- 画面全体は最大幅を持つ中央寄せとし、左右余白を常に確保する
- モバイルでは1カラムを基本とする
- `600px` を小型タブレット、`960px` をデスクトップの目安とするが、内容が崩れる位置で調整する
- desktop の広さを埋めるためだけにカラムを増やさない
- 主要操作は画面上部または内容の直後に置き、同じ重要度の操作を複数箇所へ重複させない

```css
.page-shell {
  width: min(100% - (var(--page-padding) * 2), var(--page-max-width));
  margin-inline: auto;
}
```

## 5. コンポーネント

### ボタン

操作を実行するボタンは `shared/ui/Button` を使い、役割を `variant` で選ぶ。画面ごとにボタンの色や形を書かない。

- `primary`: 画面または領域内の主要操作。原則1つ
- `secondary`: 戻る、キャンセル、再読み込み、ログアウトなどの補助操作
- `danger`: 削除など取り消しにくい操作
- タップ領域は最低 `44px × 44px`
- loading 中は連打を防ぎ、ラベルでも進行中と伝える(`disabled` と「保存中...」のような `children` を呼び出し側で切り替える)
- disabled だけで理由を伝えず、必要なら近くに説明を置く
- 遷移はボタンではなくリンク(`a`)にする

### 共通ナビゲーション

- 認証後のヘッダーは「ダッシュボード」「月別支出」「取り込む」「解析履歴」をこの順で表示する。月別支出のヘッダーリンクは今月を開き、画面内の月選択は表示中の月を保つ。
- 現在の画面は下線と `aria-current="page"` で示す。支出詳細では画面上部に遷移元へ戻るリンクを置き、直接URLを開いた場合は購入月の月別支出へ戻す。
- 900px以下ではヘッダーを2段にし、600px以下ではナビゲーションを2列にする。固定下部バーは置かない。各リンクは高さ44px以上を保つ。

### 共通入力と状態バッジ

- 入力と選択欄の共通形は `globals.css` の `.field-control` を使う。幅と配置は画面側で決め、エラーは `aria-invalid` と入力直下の文言で示す。
- 解析状態は `shared/ui/StatusBadge` で表示し、色の役割と日本語ラベルを対にする。画面固有CSSに同じ状態色を重複定義しない。
- 金額は `.amount` と `formatYen` を併用し、計上額を主、読取金額・調整額・明細金額を文脈に応じて補助として示す。
- 一覧はPCで表、狭い幅ではラベル付きの縦配置を基本にし、空状態には次の操作へのリンク、エラー状態には再試行または戻る導線を添える。

### フォーム

- ラベルは常時表示する
- 補足、入力、エラーの順序を画面間で揃える
- validation error は該当入力の直下に具体的に表示する
- 必須・任意を明示し、色だけで区別しない
- 金額入力では単位と負数の意味を示す
- 保存前に計上額がどう変わるか確認できるようにする

### カードと一覧

- カードは情報のまとまりを示す場合に使い、すべてを枠で囲まない
- 一覧の行全体が遷移する場合は、遷移先と分かる表現にする
- モバイルでは表を無理に横スクロールさせず、ラベル付きの縦配置へ切り替える
- 空の一覧には「データがない」だけでなく、作成方法または次の操作を示す

### 読み込み表示

- 画面の初回 loading はレイアウトの `Suspense` が `Spinner` で受ける。画面ごとにスピナーを書かない
- 一覧を残したまま一部だけ待つ場合(支出パネルなど)は、その領域に `Suspense` と `ErrorBoundary` を置き、失敗時は領域の中で再試行できるようにする
- 定期取得(polling)はしない。非同期に進む状態は利用者が「再読み込み」で確かめる。再取得中は現在の内容を維持してスピナーで置き換えず、ボタンのラベルで伝える。連打を防ぐため再読み込みのあと 3 秒はボタンを無効にする
- 操作(アップロード、保存)の進行中はボタンのラベルで伝え、連打を防ぐ
- `Spinner` には何を待っているかが分かる `aria-label` を付ける。`prefers-reduced-motion` では静止した表示になる

### 状態表示

解析依頼の表示名はユビキタス言語に従う。

| 状態 | 色の役割 | 表示上の配慮 |
| --- | --- | --- |
| アップロード待ち | neutral | 有効期限または待機中であることを示す |
| 解析中 | info | 進行中で操作不要と伝える |
| 登録完了 | primary / success | 支出詳細への導線を示す |
| 登録対象なし | neutral | 正常終了だが登録がないことを説明する |
| 期限切れ・停滞 | warning | 再アップロードまたは再解析を案内する |
| 解析失敗 | danger | 理由と回復操作を併記する |

バッジの色だけでなく、必ずテキストを表示する。

## 6. 画面状態

すべてのデータ表示領域について次を設計する。

- 初回 loading: skeleton または短い進行表示
- 更新中: 現在の内容を可能な限り維持し、更新中であることを補助表示
- empty: 状況説明と次の操作
- error: 利用者向けの説明、再試行、入力を失わない配慮
- success: 完了通知と結果への導線

解析は非同期であるため、「アップロード完了」と「支出の登録完了」を同じ成功として扱わない。

## 7. レスポンシブ方針

主要な確認幅は次とする。

| 幅 | 想定 |
| ---: | --- |
| 360px | 小型スマートフォン |
| 390px | 標準的なスマートフォン |
| 768px | タブレット |
| 1280px | デスクトップ |

- 360px で横スクロールを発生させない（意図したグラフ等を除く）
- desktop で本文の1行が長くなりすぎないよう最大幅を使う
- hover だけで情報や操作を出さない
- safe area がある端末でも主要操作が隠れないようにする

## 8. アクセシビリティ

- WCAG 2.2 AA を目標とする
- 通常テキストのコントラスト比は 4.5:1 以上を確保する
- focus indicator を明確に表示する
- prefers-reduced-motion を尊重する
- animation は状態理解を助ける短いものに限定し、操作完了を遅らせない
- エラー概要から該当入力へ移動できるようにする
- グラフの内容は、同じ値を読めるテキストまたは表でも提供する
- 日付や金額は読み上げ時にも意味が分かる表記にする

## 9. 文言

- 利用者には日本語を使い、内部エラーや HTTP ステータスをそのまま表示しない
- 「データ」「処理」「失敗しました」だけの曖昧な表現を避ける
- ボタンは「はい」ではなく「再解析する」「変更を保存」のように操作結果を書く
- `AI由来`、`手動編集済み` など、仕様で定義された言葉を画面間で統一する
- 破壊的または費用を伴う可能性がある操作は、実行前に結果を説明する

## 10. デザイン変更の運用

新しい画面を実装するときは、画面単位の独自 CSS より先に、既存のレイアウト、トークン、共通 UI で表現する。共通パターンが増えた場合は、この文書と `shared/ui` を同じ変更で更新する。

画面仕様にない重要な操作や項目をデザインだけで追加しない。必要性を画面仕様へ反映してから実装する。
