# 商品別税率の補完

## 目的と適用範囲

Issue #105。AI が読み取った印字情報を保持し、商品別税率を税率別対象額と照合して補完する。`analysis/domain/InferDetailTaxes` が合計選択後・商品行の登録前に実行する。支払合計と商品印字額を書き換えず、税額配分には既存の `AllocateDetailTaxes` を使う。

## 読み取り契約

- `details[].tax_mark`: 商品行の印の原文。ない場合は空文字。
- `tax_marks[]`: `mark`、`rate`、`note`（印の意味を示す注記原文）。注記や税率が不明な印は税率の確定に使わない。印がないだけで10%としない。
- `tax_breakdown[].taxable_amount`: 税抜対象額。`gross_amount` は税込対象額。どちらも印字がなければnull。
- `details[].discount_amount`: 印字行金額からさらに引く、商品への帰属が分かる値引き（正の整数円）。反映済みなら0、帰属不明ならnull。値引きは金額候補にも残す。
- `tax_rate` は印字から読み取れる税率だけを受け取る。商品情報による推定と、印字から読めた事実を混同しない。

## 補完条件

1. 読取税率と印・注記を照合する。相反する税率や注記は矛盾として残す。
2. 商品合計−値引きが税抜対象額合計と一致して税額を足すと支払合計になる場合は外税、税込対象額合計・支払合計と一致する場合は内税として、不明な課税方式を補完する。両方成立する場合は補完せず、元の方式を保持する。
3. 対応する税率群は8%・10%の1〜2群、群内で共通の内税または外税。同率の重複や内外税混在では補完しない。
4. 外税は税抜対象額と印字税額、内税は税込対象額（または税抜対象額＋税額）と印字税額を必要とする。印字税額が税率計算の切り捨て〜切り上げの範囲外なら矛盾とする。この端数条件は、店固有の規則を推測して許容幅を拡大するものではない。
5. 商品合計−値引合計が税率群の対象額合計と一致し、対象額と外税から得た支払額も採用合計と一致することを求める。数量は行金額に反映済みであり掛け直さない。
6. 商品別値引きの帰属が分かれば、その分を引いた金額で探索する。帰属不明の値引きがある混在税率は未確定。単一税率なら所属群が自明なので群全体で照合する。商品への値引き配分はしない。
7. 印字税率を固定して不明行の組み合わせを探索する。全体で一意の場合だけ不明行の税率・内外税を補完する。金額だけでの一意性は読み取り自体の正しさを保証しない。

税率別対象額・税額が不足する場合、印字から取得済みの税率や内外税は保持する。金額や印字が矛盾する場合は、誤った税込み確定を防ぐため有効な商品別税情報を未確定に戻し、元の値は解析根拠へ保存する。

## 複数候補と探索上限

- 動的計画法で同じ部分和の上位2経路を保持し、一意性・最良候補・次点を判定する。候補の優劣が同じ場合は元の行順に基づくマスク順で決定的に並べるが、これを根拠に確定しない。
- `solutions=2` は2通り以上。`states` は試みた遷移数。最大50明細・250,000遷移で打ち切り、`search_limit` とする。探索途中の最良候補を採用しない。
- 順位付けでは `food` の8%、`daily_goods` / `clothing` の10%を各1点、限定した商品名の手掛かりを2点とする。他カテゴリを一律10%にはしない。詳細な語彙は `taxPreference` を正とする。
- 最良と次点が同点なら未確定。差があれば最良候補を `suggested_tax_rate` として保存するが、**複数解は差の大小によらず自動確定しない**。スコアは確率ではなく、正解付き画像による自動採用閾値の校正が十分でないため、利用者の確認を必要とする。
- 候補なし、税率群の欠落、非対応税率・混在方式、値引き帰属不明、探索上限は未確定。印字額を書き換えて一致させない。

## 保存と表示

`analysis_evidence` に `tax_marks`、`tax_inference`（バージョン・状態・理由・解数・スコア差・遷移数）、商品別の元の商品名・印字額・数量・カテゴリ・税率・内外税、印、値引額、採用税率・候補・理由を保持する。元画像やAI生応答の保持期間に依存せず判断を追跡できる。

`expense_details` と `GET /expenses/{expense_id}` の各明細には次を追加する。

| フィールド | 意味 |
| --- | --- |
| `tax_status` | `printed` / `reconciled` / `estimated` / `unresolved` / `user_confirmed`。旧データは未設定 |
| `tax_reason` | 判定理由のコード。画面では日本語に変換 |
| `suggested_tax_rate` | 複数候補から選んだ推定税率。確認済みの `tax_rate` と区別 |

- `printed`: 印字から取得した税率。`printed_mark` なら印と注記が根拠。
- `reconciled`: 金額制約から一意に補完した税率。
- `estimated`: 商品情報で順位付けした候補。`tax_included_amount` を設定せず、カテゴリ別集計には印字額を使う。
- `unresolved`: 根拠不足または矛盾。理由を表示する。`tax_status` は税率判定の状態であり、税込み額の有無とは独立。内税の印字額が分かる旧来のケースなどでは税率未取得でも税込み額を持つ場合がある。
- `user_confirmed`: 編集画面で利用者が明示的に確定したもの。

支出詳細の閲覧・編集で根拠または未確定理由を表示する。推定値を編集フォームへ自動入力せず、既存の税区分・税率・税込み額の入力で確認する。名前・カテゴリ変更は該当行の推定候補を破棄し、印字額変更は税情報を破棄する。税情報以外の編集で推定が確定に変わることはない。

月次集計は既存の `tax_included_amount` の有無で確定件数を数える。推定の追加による月別API・集計式の変更は不要。

## 互換性と既存データ

- 新フィールドのない旧AI応答と旧DBレコードは読み取り可能。APIは追加フィールドで拡張し、frontend / backendの配布順に依存しない。
- 新規解析でのみ補完する。既存支出の一括更新は行わない。再解析が利用者編集済みの支出を上書きしない既存の条件を維持する。
- 手動確認は推定候補を削除する。支出変更時も元の `analysis_evidence` は解析時点の監査根拠として保持し、現在の明細の税情報とは区別する。

## 検証

- `detail_tax_inference_test.go`: 西友、ファミマ、単一・混在税率、印・注記、個別値引き、複数解・順位付け、読取漏れ、矛盾、探索上限。小規模な100例で全探索との一致を検証。
- analyzer / application: 新しい読み取り項目の変換、補完根拠の保存、推定が確定金額へ混ざらないこと。
- registrar / repository: 根拠と候補の永続化、変更後の再取得、手動確認時の推定候補除去、集計基準。
- frontend: 補完と推定の表示、推定が未確定から始まり確認操作後に保存されること。
- 画像による評価は [モデル評価資料](./receipt-analysis-models.md) に記録する。金額一致だけで商品税率の正解とみなさない。
