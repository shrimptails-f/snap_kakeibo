# レシートのトリミング評価

## 目的

[#106](https://github.com/shrimptails-f/snap_kakeibo/issues/106) の手動トリミング・自動提案を評価する。画面契約は [アップロード画面](./screens/upload/README.md#送信前のトリミング)。2026-09-24に実施した少数の試験であり、一般的な読取精度や実機性能は保証しない。

## 実装と判断

- 縦横比を固定しない矩形とし、EXIFの向き補正済みの元画像に対する割合座標を保持する。切り取りは元解像度から行い、JPEG品質0.95 / PNGで出力する。再編集も元画像から行う。
- 自動提案は追加依存なしのWeb Workerで実行する。長辺480px以下、明度閾値130 / 170 / 210と色差65未満の連続領域を探索する。矩形面積6〜90%、充填率65%以上、輪郭の平均明度差22以上などを組み合わせて候補を評価する。重なる領域は影で紙の一部だけを残さないよう広い候補を優先する。
- 候補が競合する場合、上端・左右まで紙が続く場合、5秒以内に検出できない場合は全体から手動操作に戻す。各辺に画像寸法の3%の余白を加え、自動では切り取りを確定しない。
- OpenCV.jsは導入しない。現段階の矩形提案には標準APIで対応し、配信・初期化の負担を抑える。台形や湾曲の補正は行わない。

## 実画像の読み取り比較

前回 #105 で利用者が提示した原画像2枚（各3024×4032px）を端末内の評価用コピーから使用した。目視で店名・商品・日付・合計を残すよう、画面の手動操作で以下の範囲を確定した。原画像・解析結果を既存の支出へ書き戻していない。

| 画像 | 元画像に対する範囲（左・上・幅・高さ） | 正解 |
| --- | --- | --- |
| ファミリーマート | 15%・15%・70%・85% | 11商品、商品合計3,992円、値引10円、支払3,982円、8%内税294円 |
| 西友 | 10%・0%・75%・100% | 6商品、税抜2,006円、10%税200円、支払2,206円 |

両条件とも同じブランチの `OpenAIReceiptAnalyzer.Analyze` と `ResizeJPEG` を使い、`gpt-5.6-terra` / `medium`、長辺最大2048px、`high`、同じ指示文・JSON Schemaで各1回、計4回実行した。比較は税率補完前の読み取り内容を対象とする。全体画像に拡大画像を追加する方式ではない。

| 指標 | ファミマ・元 | ファミマ・切り取り | 西友・元 | 西友・切り取り |
| --- | ---: | ---: | ---: | ---: |
| 読み取った商品行数 / 正解 | 8 / 11 | 11 / 11 | 6 / 6 | 6 / 6 |
| 正解に対する行数不足 | 3（対応不明の誤読もあり） | 0 | 0 | 0 |
| 商品行金額 | 商品名との対応が崩れており正解率を算出しない | 11 / 11一致 | 3 / 6一致 | 6 / 6一致 |
| 最終支払合計 | 3,982円 | 3,982円 | 2,206円 | 2,206円 |
| 税額 | 295円（正解294円） | 294円 | 200円 | 200円 |
| API応答時間 | 55.8秒 | 13.0秒 | 44.9秒 | 20.9秒 |

誤読の具体例:

- ファミマの元画像は「おーいお茶」に159円を対応させ（正解186円）、存在しない「マカロニ・フジッロ」「パンテカミーノ」などを出力した。切り取り後は金額・数量・値引が全商品で一致したが、「具だくさん！チキン南蛮」を「真たくあん！チキン南蛮」とする商品名の誤読が残った。
- 西友の元画像は516→258円、369→398円、6→235円と3行の金額を誤読し、雑巾・マジックリンの数量も誤った。切り取り後は6行の金額・数量が一致した。

今回の2例では手動の余白除去後に商品行の読み取りが改善した。ただし各条件1回でモデル出力の揺れを含み、応答時間の短縮や他画像での改善を保証しない。商品名の誤読は [#107](https://github.com/shrimptails-f/snap_kakeibo/issues/107) の継続課題とする。

## 自動提案と処理時間

- 合成画像の長い紙・横長の紙・影と軽い傾きを含む紙は、外接範囲と余白を含む候補になる。
- 合成画像の白背景・同程度の紙が2枚・境界欠け・候補なしは全体選択になる。
- 初版の実写真2枚はいずれも紙の下端が写真外まで続くため、候補なしとして全体選択になった。文字の途中で自動的に切らず、手動操作へ進める。この試験では自動化の効果を確認できなかった。
- Chromium、390×900px、CPUを4倍遅くするエミュレーションで、検出用画像の画素取得後に検出関数を各5回実行。ファミマ47.7〜116.1ms（中央値50.8ms）、西友70.0〜92.0ms（中央値88.7ms）。画像の読み込み・縮小・Workerの起動時間はこの数値に含まない。
- 本番ビルドのWorkerは1.72kB。主JSは580.82kB（変更前572.58kB）、CSSは43.05kB（変更前41.70kB）。外部モデル・画像処理ライブラリのダウンロードはない。
- 物理スマートフォン・Safariでの処理時間、低メモリ端末、大きく湾曲・斜めになった写真、幅広い背景条件は未検証。CPU制限による測定は実機の代用となる保証はない。

## 操作と競合の検証

- Chromiumの360 / 390 / 768 / 1280pxで横あふれなし。枠移動・四隅調整、適用、再編集、全体へ戻してキャンセル、未編集へ戻す、Escape、操作元へのフォーカス復帰を確認した。
- キーボードの矢印・Shift併用とマウスのPointer Capture、390pxのタッチイベントでサイズ変更を確認した。
- 4色のJPEG検証画像にEXIF Orientation 1〜8を付け、各向きの左上4分の1を画面操作で切り抜いた。8種類すべてで出力寸法と中心画素が向き補正後の正解と一致した。
- 単体・hookテストで、画像ごとの独立性、確定Fileでの送信・再試行、元画像への復帰、URL解放、手動調整後・キャンセル後の古い検出結果の無視、出力中のキャンセル、出力失敗、Worker未対応、検出タイムアウトを確認する。
- 実機カメラとiOS Safariでの操作は未検証。追加写真・実機の検出評価は #106 の残確認項目として扱う。

- 実画像比較では同じ元画像と正解転記を使用し、上表の割合範囲で手動適用する。モデル、effort、指示文、schema、縮小上限を揃え、保存APIを呼ばずに解析だけ実行する。今後は複数回の試行と実機・写真条件を増やして評価する。


## 下端の見切れへの追加対応（2026-09-25）

- 対象は背景と紙の境界が明瞭な写真、および下端が見切れた写真の左右の余白除去。白い机・強い影・折れ・大きな傾きへの追加対応は見送る。
- 下端に接する候補を一律に棄却する条件を変更した。候補を構成する画素から各行の左右端を求め、各端の内外4画素の平均明度差が両側とも22以上である行が70%以上の場合に限り採用する。文字などの内部エッジが強いだけでは採用しない。
- 下端の見切れ候補は左右に3%の余白を加え、高さは元画像全体を残す。「左右の余白を提案しました。上下は画像全体を残しています」と表示し、適用は利用者が行う。
- 合成画像で下端見切れの左右提案・高さ維持を確認する。低コントラスト、片側が背景と同化した画像、複数候補、左右や上端の見切れは全体選択を維持する。従来の明瞭な長方形の提案も回帰検証する。
- 前回の実写真2枚は今回も候補なし。明度閾値による連続領域が既存の面積・充填率・端位置の条件を満たさず、今回の左右判定まで進まなかった。今回の対応によって、この2枚で自動提案が成功するとは主張しない。
- Chromiumの360 / 390 / 768 / 1280pxで手動調整・適用・キャンセル・復帰と横あふれなしを再確認した。読取モデル・送信画像の生成方法は変更せず、外部APIによる読み取り比較は再実施していない。
- 390pxの実ブラウザで、文字を含む下端見切れの検証用PNG（1200×1600px）を選択し、左右提案の案内と適用を確認。提案は左22%・幅56%で、出力672×1600pxとなり高さを維持した。
- `pnpm lint` は警告0、`pnpm test` は20 files / 126 tests成功、`pnpm build` は成功。Worker 2.22kB、主JS 580.99kB。既存の500kB超チャンク警告1件。依存ファイルの差分なし。
