# レシート解析モデルの比較

## 目的

レシート画像から店名、購入日、合計金額、明細、カテゴリを取得する OpenAI モデルを選ぶために、モデル名、`reasoning.effort`、コスト、精度の期待値を整理する。

価格とモデル仕様は 2026-09-23 時点の公式 OpenAI ドキュメントに基づく。価格や提供条件は変更される可能性があるため、モデル変更時には公式資料を再確認する。

## 現在の設定

dev 環境では次を使用する。

| 項目 | 現在値 |
| --- | --- |
| モデル名 | `gpt-5.6-terra` |
| `reasoning.effort` | `medium` |
| API | Responses API |
| 画像 | 長辺2048px以下のJPEG、`detail: high` |
| 出力 | Structured Outputs、`strict: true`、最大8192トークン |

モデルと effort は `infra/config/dev.go` を正とし、Analyze Lambda の `OPENAI_MODEL` と `OPENAI_REASONING_EFFORT` に渡す。

## 比較対象

比較対象は、Responses API、画像入力、Structured Outputs に対応する現行の汎用モデルとする。精度の期待値は公式のモデル位置付けから置いた**レシート解析向けの仮説**であり、OpenAI が公表したレシート読取精度や本プロジェクトの実測値ではない。

| モデル | APIモデル名 | 対応effort | 比較開始時のeffort | 標準料金（入力 / キャッシュ入力 / 出力、100万トークンあたり） | レシート解析精度の期待値 | 備考 |
| --- | --- | --- | --- | --- | --- | --- |
| GPT-5.6 Luna | `gpt-5.6-luna` | `none` / `low` / `medium` / `high` / `xhigh` / `max` | `medium` | $0.20 / $0.02 / $1.20 | **低コスト側の比較基準**。鮮明で単純なレシートの定型抽出には十分と期待する。かすれ、複雑な割引、複数税率、長い明細で上位モデルとの差が出る可能性がある | 以前の設定。高頻度・コスト重視向け。旧GPT-5系のnano相当という位置付け |
| GPT-5.6 Terra | `gpt-5.6-terra` | `none` / `low` / `medium` / `high` / `xhigh` / `max` | `medium` | $2.00 / $0.20 / $12.00 | **現在の品質基準**。Lunaよりレイアウト解釈、商品行と小計・税・割引行の区別、カテゴリ分類の改善を期待する | 現在値。品質とコストの均衡候補。Lunaに対し入力10倍、出力10倍の単価 |
| GPT-5.6 Sol | `gpt-5.6-sol` | `none` / `low` / `medium` / `high` / `xhigh` / `max` | `medium` | $4.00 / $0.40 / $20.00 | **高い期待**。判別しにくい行、曖昧な店舗名、複雑な明細の評価上限を確認する候補 | GPT-5.6のフラッグシップ。`gpt-5.6` はこのモデルへのエイリアス。公式ページ記載の価格は少なくとも2026-11-21までのプロモーション価格 |
| GPT-6 Astra | `gpt-6-astra` | `low` / `medium` / `high` / `xhigh` / `max` | `low` と `medium` | $10.00 / $1.00 / $50.00 | **最も高い期待**。難読画像や複雑な判断に対する上限モデル。ただし、OCR精度が単価に比例する保証はない | 公式上の最上位モデル。`none` は非対応。通常運用より、失敗例の診断や比較評価の上限として先に試す |

価格は短いコンテキストのStandard処理を記載する。このアプリの1リクエストは272K入力トークンを大きく下回る想定だが、実使用量はAPIレスポンスの`usage`で確認する。

## コストの見方

実コストは画像の縦横サイズ、画像detail、指示文、Structured Outputs、生成された出力・推論トークンに依存する。そのため「レシート1枚あたり」の固定価格は置かず、次で計算する。

```text
概算USD = 非キャッシュ入力トークン数 × 入力単価 / 1,000,000
        + キャッシュ入力トークン数 × キャッシュ入力単価 / 1,000,000
        + 出力トークン数 × 出力単価 / 1,000,000
```

同じリクエストが入力2,500トークン、出力500トークンだった場合の単純比較は次のとおり。画像トークン数がモデル間で同じになることを保証するものではなく、相対的な単価差を見るための例である。

| モデル | 1リクエストの例 | Luna比 |
| --- | ---: | ---: |
| `gpt-5.6-luna` | $0.0011 | 1.0倍 |
| `gpt-5.6-terra` | $0.0110 | 10.0倍 |
| `gpt-5.6-sol` | $0.0200 | 約18.2倍 |
| `gpt-6-astra` | $0.0500 | 約45.5倍 |

円換算は為替で変動するため文書には固定しない。画像1枚あたりの見積もりは、実際に送る2048px以下の画像サイズとモデルを[画像入力トークン数・コスト計算ツール](https://developers.openai.com/api/docs/guides/image-cost-calculator)へ入力し、実レスポンスの`usage`と突き合わせる。

## effortの選び方

| effort | このアプリでの扱い |
| --- | --- |
| `none` | 最低レイテンシ・低コストの比較用。商品行の判定とカテゴリ分類を含むため、初期の本番候補にはしない。Astraでは使用不可 |
| `low` | 鮮明で単純なレシートに対するコスト削減候補。`medium`と同じ評価セットで精度を比較する |
| `medium` | 現在値かつモデル比較の基準。モデル差を比較するときは、まず全モデルを`medium`に揃える |
| `high` | `medium`で失敗する複雑なレシートの追加実験用。全リクエストへ一律適用しない |
| `xhigh` / `max` | 難例でモデル能力の上限を見る評価用。コストとレイテンシを計測し、改善が確認できた場合だけ採用を検討する |

effortを上げても、ぼけ、白飛び、文字の画素不足など入力画像に情報がない問題は解消しない。モデル変更・effort変更の前に、画像縮小後の可読性も確認する。

## 精度評価

モデル名だけで採用を決めず、同じ画像、指示文、JSON Schema、`detail: high`で比較する。少なくとも次の種類を含む正解付き評価セットを用意する。

- 一般的なスーパー・コンビニのレシート
- 細長いレシート、明細数が多いレシート
- かすれ、傾き、影、折れ、反射がある写真
- 値引き、クーポン、小計、税、預り金、お釣りが混在するレシート
- 複数税率、数量表記、返品・負数を含むレシート
- レシートではない画像

モデル・effortごとに次を計測する。

| 指標 | 見る内容 |
| --- | --- |
| 店名一致率 | 正規化後の店名が正解と一致した割合 |
| 購入日一致率 | `YYYY-MM-DD`の完全一致率 |
| 合計金額一致率 | 支払額の完全一致率。小計・預り金との取り違えを個別集計する |
| 税額・小計との取り違え | 税額、税抜対象額、小計を `read_amount` に採用した件数 |
| 税区分と低確度 | 内税・外税・混在・不明の判定一致率と `analysis_evidence.status=weak` の件数 |
| 明細精度 | 商品行の過不足、商品名、金額、数量の一致率 |
| カテゴリ一致率 | 定義済みカテゴリとの一致率 |
| 終端状態 | `SUCCEEDED` / `NO_DATA` / `FAILED`の妥当性、refusal、incomplete、Schema不一致率 |
| コスト | 1枚あたりと成功1件あたりの入力・出力トークンおよびUSD |
| レイテンシ | API呼び出しのp50 / p95と各試行5分・合計10分30秒のタイムアウト率 |

現在は `gpt-5.6-terra` / `medium`を品質基準とする。同じ評価セットで以前のLunaと比較し、品質目標を満たすか確認する。Terraで品質目標に届かなければSol、Astraの順に比較し、十分な余裕を持って目標を満たす場合はTerraの`low`も試す。最終的には、品質目標を満たす中で最も低コストかつ低レイテンシの組み合わせを採用する。

## 商品別税率の補完の評価（#105、2026-09-24）

[商品別税率の補完](./receipt-tax-inference.md)を追加した。指標に商品別税率の正解率、補完率、誤確定率、未確定率、探索時間を加える。金額合計の一致と商品行の正しさを別に評価する。

### 原画像との照合

利用者が提示したdevの2支出から原画像・保存済み解析根拠を取得した。モデルはdevの `gpt-5.6-terra` / `medium`、画像は現行と同じ長辺2048px・`high`。支出への書き戻しは行っていない。最終指示文による全体画像各1回の結果は次のとおり。

| 指標 | 西友 | ファミリーマート |
| --- | --- | --- |
| 原画像の正解 | 6商品、税抜2,006円、10%税200円、支払2,206円 | 11商品、商品合計3,992円、値引10円、支払3,982円、8%内税294円 |
| 保存済み解析の合計 / 商品行数 | 2,206円 / 6行 | 1,982円 / 8行 |
| 変更後の読み取りの合計 / 商品行数 | 2,206円 / 6行 | 3,982円 / 6行 |
| 変更後の税率判定 | 全6行10%に補完 | 1行のみ印から8%、残り不明、税率別内訳欠落 |
| 変更後の税込み額未確定 | 0 / 6行 | 6 / 6行 |
| 商品印字額の確認 | 4 / 6行一致。369→370円、6→5円の相殺する誤読 | 商品名・金額の対応と行数が崩れ、商品単位の対応を確定できない |
| API読み取り〜照合の時間 | 60.2秒 | 43.7秒 |

最終合計の一致は保存済み1/2件から今回2/2件になったが、商品行の精度は改善を確認できていない。西友の採用税率は6/6行正しい一方、2行は金額の誤読を残したまま税込み換算される。ファミマは明細対応が崩れているため、商品単位の税率正解率・誤確定率は算出しない。少数の単発試験からモデル全体の精度や改善率を主張しない。

同一画像の上部・下部の拡大部分を追加する試験も各1回行ったが、ファミマ8行・西友5行となり、いずれも金額不一致で未確定になった（約55.8秒 / 55.8秒）。効果を確認できなかったため、この画像追加方式は本実装に含めない。商品行の読み取り改善は [#107](https://github.com/shrimptails-f/snap_kakeibo/issues/107) で継続する。

### 計算部分の評価

- 原画像を目視転記した正解金額・税率別内訳を入力すると、西友6商品は10%・外税、ファミマ11商品は8%・内税になり、17/17行の税率・内外税を判定できる。印字額と店舗値引きを変更しない。
- 商品情報から順位付けする複数解は提案に留め、未校正のスコア差で自動確定しない。
- 小規模100例で動的計画法の上位2候補と全探索結果が一致する。50明細の同額混在例は探索上限に達せず、金額が異なる多数の部分和は上限で未確定に戻る。
- `go test ./internal/analysis/domain -run TestFamilyMartIssue105 -bench BenchmarkInferDetailTaxes50Rows -benchtime=100x -count=1` による50明細例は約0.321ms/回（Linux amd64、Core i5-13400F）。単体ベンチマークでありAPIのp95を示す値ではない。

これらは計算部分の回帰確認であり、画像読み取り精度の保証ではない。原画像・AI生応答・認証情報はリポジトリへ保存していない。
