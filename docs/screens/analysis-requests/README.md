# 解析依頼一覧画面（解析履歴）

アップロードからの一連の流れは [アップロード画面・解析状況](../upload/README.md) を参照。

## 目的

取り込み後に画面を離れた利用者が、画像ごとの解析状況を見つけ直し、支出の確認や失敗からの回復へ進む。

設計対象: [Issue #77](https://github.com/shrimptails-f/snap_kakeibo/issues/77) の解析依頼一覧画面。`/analysis-requests` には現行APIで表示できる受付月の履歴、状態、再解析・再アップロード・支出詳細への導線を実装済み。月選択、状態絞り込み、ページネーション、店舗名・計上額はAPI拡張を伴う後続実装とする。[アップロード画面](../upload/README.md) と合わせて読む。

## 操作できるモック

[mock.html](./mock.html) をブラウザーで開くと、検索条件カードと履歴カード、画像単位の表をサンプルで確認できる。受付月・状態の絞り込み、ページ切り替え、再読み込み、再解析を試せる。APIには接続せず、実際の画像送信や支出登録は行わない。9月25件・8月3件・7月0件のサンプルで、20件ごとのページ切り替えを確認できる。再解析による変更はブラウザーでページ全体を再読み込みすると初期値に戻る。

支出詳細は既存の見本を別タブで開き、解析履歴の表示位置を保つ。選択行ごとの支出データとの連携は行わない。アップロードへの操作は [アップロードのモック](../upload/mock.html) へ移動する。撮り直しでは対象ファイル名を渡すが、履歴のサンプルと新しい取り込み結果は共有しない。下部の「モックの表示状態を切り替える」から空状態を確認できる。

ローカルサーバーで確認する場合は、リポジトリルートで次を実行する。

```sh
python3 -m http.server 4176 --directory docs/screens
```

`http://localhost:4176/analysis-requests/mock.html` を開く。サンプルによるページ切り替えは表示確認用であり、後述するAPIのページネーション拡張を実装したものではない。

## 役割と遷移

- 履歴は画像1枚（`analysis_request_id`）を1行とする、ページネーション付きの表にする。一括アップロードの単位ではまとめない。再解析は同じ行の状態・試行番号を更新し、再アップロードは新しい行になる。

- 独立画面 `/analysis-requests` を維持し、利用者向けの見出し・ナビゲーションは「解析履歴」にする。アップロード画面では「今回」、ここでは月単位の履歴を扱う。
- `/analysis-requests?month=2026-09&filter=attention` のように月と絞り込みをURLへ保持する。省略時は現在の受付月・すべて。無効な値は既定値へ戻す。
- 月は依頼の受付月（APIの `year_month`）で、レシートの購入月ではない。月選択には「受付月」と明記する。
- `支出詳細を見る` は `/expenses/:expenseId` へ進む。戻るときは元の月・絞り込み・ページ・一覧位置を復元する。支出詳細側の既存文言「解析依頼一覧へ」は、この画面実装に合わせて「解析履歴へ」に統一する。
- `レシートを取り込む` は緑の主要ボタンとして表示し、`/upload` へ進む。PCではページ見出しの右、スマホでは見出しの下に置く。履歴なしの案内内でも同じボタン表現を使う。実装時は遷移用リンクにボタンのスタイルを適用する。期限切れなどから来た場合は対象ファイル名と案内を渡し、再選択・撮影から始める。

## カード構成

検索条件と履歴を別々のカードに分け、PC・スマホとも上から順に配置する。

| カード | 内容 |
| --- | --- |
| 検索条件 | 受付月、状態の絞り込み、購入月との違いの説明、`要対応を見る` |
| 履歴 | 適用中の受付月・状態、状態確認時刻、`再読み込み`、画像単位の表、ページネーション |

- 条件は選択変更時に適用して先頭ページを取得する。履歴カードにも適用中の条件を表示し、何の結果か分かるようにする。
- 両カードは共通の白いsurface・border・角丸（`--radius-md`）を使う。カード間は24px、内側の余白はスマホ16px・PC24pxを基本とする。
- 履歴の各画像は1つの履歴カード内の行として罫線で区切る。検索条件カードと履歴カードは幅を揃える。
- 履歴の読み込み中・空状態・取得失敗は履歴カード内で表示する。検索条件カードを残し、条件変更で探し直せるようにする。

## 記号の凡例

`[ 操作 ]` はボタン、`[ 値 v ]` は選択欄、`リンク >` は遷移。`…` 進行中、`✓` 登録完了、`－` 登録対象なし、`!` 注意、`×` 失敗。色と記号だけでなく状態名を表示する。日時・件数は説明用の例。

## ページネーション

- 1ページ最大20画像を設計上の初期値とし、PC・スマホで揃える。図では説明のため4行のみを載せている。
- 表の下に `前へ` / `Nページ目` / `次へ` を置く。総件数・総ページ数・任意ページへのジャンプは表示しない。先頭では `前へ`、続きがない場合は `次へ` を無効にする。
- 受付日時の新しい順を維持する。同時刻の画像も順序が安定するようAPI側で依頼IDを使う並び順を確定する。
- 受付月・絞り込みを変えたら先頭ページへ戻す。絞り込みは月全体を対象にし、表示中の20件だけを絞って「該当なし」としない。
- ページ切り替え中は前の行を残して「次のページを読み込み中」などと表示し、行の操作とページ切り替えを無効にする。取得成功後にページ番号を確定して表の先頭へ移動する。失敗時は元のページに留まり、操作を戻して再試行を案内する。
- `再読み込み` は同じページの取得条件で実行し、通常はページ・スクロール位置を保つ。状態変更によってページが空になった場合はその旨と `前へ` / `先頭へ戻る` を出す。先頭ページの空状態とは区別する。
- 詳細への遷移時は、月・絞り込み・現在ページのカーソル・前ページへ戻るための履歴・一覧位置を保持する。戻ったときは同じページを再表示する。復元できない場合は「表示位置を復元できなかったため、先頭から表示しています」と案内する。
- カーソルによる続きの取得を前提とする。ページ番号はその条件で先頭からたどった位置を示し、固定のページ番号による直接参照は提供しない。

## 絞り込み・更新

| 表示 | 含める状態 |
| --- | --- |
| すべて | 選択した受付月の全状態 |
| 要対応 | 期限切れ、停滞、解析失敗 |
| 進行中 | 有効期限内のアップロード待ち、停滞していない解析中 |
| 登録完了 | `SUCCEEDED` |
| 登録対象なし | `NO_DATA`。失敗とは分ける |

- フィルターはAPI側で受付月全体へ適用した上でページを返す設計とする。同じ区分・文言をアップロード画面でも使う。期限切れ・停滞の閾値は下の状態表と揃える。
- 初回と受付月変更時に取得する。定期取得はせず、`再読み込み` で状態を確認する。取得中は現在の一覧を保ち `再読み込み中…` とする。再読み込み後5秒は連打を防ぐ。クールタイム中はボタン内を左から薄い緑で満たし、残り秒数も表示して、再び操作できるまでの時間を色だけに頼らず伝える。
- 表示時と再読み込み時に期限切れ・停滞を判定する。ページ取得時の絞り込み判定との時刻差で区分が変わった場合は、再読み込みで一覧を揃える。「状態確認」の時刻で最新性を示し、実際の完了をリアルタイムで把握しているように見せない。
- 再解析を受け付けた行は `解析中` に更新する。`要対応` などの絞り込みから外れる場合は「再解析を開始しました。進行中で確認できます」とリンク付きで通知し、フォーカスを通知へ移す。
- 受付月変更中に前の月の一覧を残す場合は「2026年8月を読み込み中」など対象を明示して、古い行の操作を止める。失敗時も別月の内容を新しい月の結果と誤認させない。

## 回復操作

### 再解析

`再解析する` は既存の画像をもう一度解析する。アップロードからやり直す操作と区別する。

```text
┌──────────────────────────────────┐
│ この画像を再解析しますか？       │
│ receipt-04.jpg                   │
│ 保存済みの画像でもう一度         │
│ 読み取りを行います。             │
│ [ キャンセル ] [ 再解析する ]    │
└──────────────────────────────────┘
```

対象が停滞の場合は「前の解析が進行中の可能性があります。新しい試行を開始します」を追加する。確認後は対象行だけ `再解析を開始中…` とし、同じ操作の連打を防ぐ。他の行と月の閲覧は妨げない。

| 結果 | 表示・操作 |
| --- | --- |
| 成功 | `解析中` に更新し「再解析を開始しました」。結果は `再読み込み` で確認 |
| 通信失敗・結果不明 | 「再解析の受付を確認できませんでした」。まず `再読み込み` を案内し、重ねて自動送信しない |
| 状態競合（409） | 「状態が変わったため、再解析できませんでした」。最新一覧を取得して、その状態の操作へ切り替える |
| その他の受付失敗 | 「再解析を開始できませんでした」。画像と元の状態を保ち、再試行できるようにする |

### 再アップロード

期限切れや画像の撮り直しは `/upload` へ移動し、次の案内を選択欄の上に出す。

```text
receipt-01.jpg の画像をもう一度選ぶか、撮り直してください。
新しい取り込みとして登録します。
[ レシートを撮影 ] [ 画像を選ぶ（複数可） ]
```

過去のFileは復元できないため、自動で送信を始めない。元の依頼は履歴に残す。`TOO_MANY_DETAILS` は「商品明細が50件を超えています。取り込み可能な画像を選び直してください」と案内する。同じ画像の再解析や、合計を重複登録しかねない機械的な画像分割は提案しない。

## 画面状態

| 状態 | 表示・操作 |
| --- | --- |
| 初回取得中 | 共通の読み込み表示「解析履歴を読み込み中」。画面見出しと取り込みリンクは残す |
| 履歴なし | 「この受付月の取り込みはありません」。別の受付月を選ぶ操作と `レシートを取り込む` |
| 絞り込み結果なし | 「要対応の画像はありません」など選択に応じた文言と `すべてを見る` |
| 初回取得失敗 | 「解析履歴を読み込めませんでした」と `再読み込み` |
| 更新失敗 | 最後の一覧と状態確認時刻を残し「最新の状態を取得できませんでした」と `再読み込み` |
| 登録完了だが支出IDなし | 詳細リンクを出さず「支出情報を確認できませんでした」と `再読み込み`。未定義のURLへ進めない |

## 表示とアクセシビリティ

- [デザインガイドライン](../../../front/docs/design_guidelines.md) に合わせ、白背景・緑の主要操作・橙の注意・赤の失敗とする。色だけで状態を伝えない。
- 本文16px、補助14px以上を目安にし、最大幅1120px、左右余白はモバイル16px・PC24px。影やグラデーション、装飾用の指標カードを追加しない。
- 検索条件・履歴はそれぞれ見出し付きの領域にする。
- 360px / 390px / 768pxはラベル付きの縦配置。960px以上は表形式にする。ファイル名とエラー理由を折り返し、操作をhover限定にしない。
- PCの表は列見出しとセルの対応を読み上げでも伝える。スマホで縦配置にしても、画像ごとのまとまりと項目の意味を保つ。ページ切り替え領域には「解析履歴のページ切り替え」と名前を付け、現在のページを読み上げに伝える。
- 状態名、理由、次の操作の順に読む。再解析ボタンを含む行全体をリンクにせず、支出詳細は独立したリンクとする。
- ボタン・リンクは44px以上のタップ領域と明確なフォーカス表示を持つ。行の操作の読み上げ名にはファイル名を含める。
- 再解析確認ではフォーカスを閉じ込め、Escで閉じて操作元へ戻す。更新通知は読み上げに伝え、通常の再取得ではフォーカスや一覧位置を動かさない。
- 初回以外は一覧をスピナーに置き換えない。動きは操作に伴う状態変化に限定し、`prefers-reduced-motion` に従う。

## ステータス表示

バックエンドの `status` に加えて、画面側で経過時間を判定して表示を切り替える。バックエンドは期限切れや停滞で状態を変更しない。

| 表示 | 条件 | 操作 |
| --- | --- | --- |
| アップロード待ち | `status = UPLOADING` かつ `now <= upload_expires_at` | なし |
| 期限切れ | `status = UPLOADING` かつ `now > upload_expires_at` | 再アップロードを促す |
| 解析中 | `status = ANALYZING` かつ `now - updated_at <= 30分` | なし |
| 停滞 | `status = ANALYZING` かつ `now - updated_at > 30分` | 再解析ボタン |
| 登録完了 | `status = SUCCEEDED` | 支出詳細・編集画面へ |
| 登録対象なし | `status = NO_DATA` | 再解析ボタン |
| 解析失敗 | `status = FAILED` | `error_code` に応じたメッセージ + 再解析ボタン |

### error_codeごとの表示

| error_code | メッセージ | 再解析 |
| --- | --- | --- |
| `ANALYSIS_FAILED` | 画像を解析できませんでした | 可 |
| `INVALID_DATE` | 購入日を正しく読み取れませんでした | 可 |
| `INVALID_AMOUNT` | 金額を正しく読み取れませんでした | 可 |
| `NO_TOTAL_AMOUNT` | 合計金額を読み取れませんでした | 可 |
| `NO_DATE` | 購入日を読み取れませんでした | 可 |
| `TOO_MANY_DETAILS` | 商品明細が50件を超えています | 不可(再アップロードを促す) |
| `INTERNAL` | システムエラーが発生しました | 可 |

`NO_DATA` は解析完了だが登録対象の明細が0件だった状態。支出と月次集計には反映しない。

一時的な失敗はバックエンドが SQS の再配信で最大3回まで同じ試行をやり直す。それでも失敗したものや恒久的な失敗には再解析ボタンを表示する。

`TOO_MANY_DETAILS` は初期構成の仕様上扱えないため、再解析ボタンは出さない。

## API設計

### GET /months/{yyyy-MM}/analysis-requests

指定月の解析依頼を作成日時の降順で取得する。`{yyyy-MM}` が `YYYY-MM` の形式でなければ `400`。

Response:

```json
{
  "items": [
    {
      "analysis_request_id": "01JREQUESTXXX",
      "expense_id": "01JEXPENSEXXX",
      "status": "SUCCEEDED",
      "attempt": 1,
      "file_name": "receipt.jpg",
      "content_type": "image/jpeg",
      "year_month": "2026-09",
```

#### 画面設計に対して未対応の項目

以下は画面設計にあるが API が返していない。対応するときは backend / frontend / 本書を合わせて変える。

| 項目 | 用途 | 未対応の理由 |
| --- | --- | --- |
| `store_name` / `recorded_amount` | 一覧の「店舗名」「計上額」列 | `expenses` にしか無く、一覧で支出を結合していない |
| ページサイズ・継続カーソル・次ページの有無 | `前へ` / `次へ` による履歴取得 | 現行APIは続きの取得情報を返さない |
| 月全体の状態絞り込み | 別ページの要対応も検索対象にする | 現行APIは状態フィルターを受け取らない |

ページネーション拡張時は、カーソルの要求・応答フィールド、期限切れ・停滞の判定時刻、更新を挟んだ場合の順序をbackend / frontendで確定する。絞り込み後に最大20件を返し、取得途中で一致する画像がなくても続きがあれば探索を継続するか、続きがあることを示す。「この月に該当なし」は検索範囲を確認できた場合だけ表示する。現行の1回のQuery結果をフロントだけで分割して、この設計のページネーションに対応済みとはしない。

### POST /analysis-requests/{analysis_request_id}/retry

`FAILED`、`NO_DATA`、または停滞した `ANALYZING` の解析依頼に対して、新しい解析試行を開始する(再解析)。SQS による同一試行の再配信とは別の操作で、`attempt` を1増やす。

Response:

```json
{
  "analysis_request_id": "01JREQUESTYYY",
  "status": "ANALYZING",
  "attempt": 3
}
```

`status` が `FAILED` / `NO_DATA` / `ANALYZING` 以外の場合は `409 Conflict` を返す。

## 実装時の確認

- 月の選択→要対応に絞る→再解析→進行中で確認→登録完了から詳細→元の絞り込みへ戻る導線を確認する。
- 期限切れからアップロードへ進み、未選択の状態で元の画像が送信済みのように見えないことを確認する。
- 登録対象なし、再解析不可の失敗、409、再読み込み失敗、長いファイル名を確認する。
- 21件以上で次ページ・前ページを操作し、ページ取得失敗、月・絞り込み変更時の先頭復帰、2ページ目から詳細へ進んだ後の復帰を確認する。
- 現在ページに要対応がなく、別ページにだけ存在する場合も `要対応を見る` から見つけられることを確認する。APIのページネーションと月全体の絞り込みは、この画面実装の前提として対応する。
- 店舗名・計上額・画像URLの不足、支出詳細からの戻り先文言は画面実装時に整合させる。

画面設計と静的モックを提供する。実APIを使った状態更新・ページネーション・画面間の復帰はUI実装時に検証する。
