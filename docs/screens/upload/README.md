# アップロード画面・解析状況

## 目的

スマートフォンでレシートを撮影・複数選択し、画像ごとの進行を確認して、登録できたものから支出詳細へ進む。

実装対象: [Issue #81](https://github.com/shrimptails-f/snap_kakeibo/issues/81)（親: [#77](https://github.com/shrimptails-f/snap_kakeibo/issues/77)）のアップロード画面と解析状況の導線。本書の記号ベース設計と `/upload` の実装を対応させる。

## 設計方針

- 白背景と落ち着いた緑を使う、静かで読みやすい家計簿の作業画面。[デザインガイドライン](../../../front/docs/design_guidelines.md) の既存トークンを使う。
- 特徴は「画像1枚につき、現在地と次の操作が1行で分かる」こと。全件の解析完了を待たず、登録完了した画像から確認できる。
- アップロード画面 `/upload` は撮影・選択・送信と「今回の取り込み」を担当する。
- [解析依頼一覧](../analysis-requests/README.md) は独立した `/analysis-requests` として残し、画面上は「解析履歴」と呼ぶ。月をまたぐ履歴や後日の回復操作をここに集める。
- [支出詳細・編集](../expense-detail/README.md) は `/expenses/:expenseId` に分ける。アップロード画面内には編集パネルを置かない。
- 解析状況は「今回の取り込み」で確認し、解析待ち専用の全画面表示は設けない。
- 選択前は撮影、選択後は送信を主要操作にする。画像選択・追加・除外は補助操作。
- 解析状況は手動で再読み込みする。自動 polling、推定の残り時間、根拠のない解析パーセントは表示しない。

## 画面間の導線

```text
アプリの「取り込む」 → /upload
                          |
                 撮影 / 複数画像を選択
                          |
                 選択内容を確認・除外
                          |
                 [ N枚をアップロード ]
                          |
                 今回の取り込み（画像ごと）
                          |
           +--------------+----------------+
           |                               |
      登録完了                         解析中・失敗など
           |                               |
    支出詳細を見る >                [ 再読み込み ] / 回復操作
           |
 /expenses/:expenseId
           |
    < アップロードへ（元の画像・位置へ）

/upload ── 解析履歴を見る > ── /analysis-requests?month=2026-09
                                  |
                         月・状態で履歴を絞る
                                  |
                      支出詳細 / 再解析 / 再アップロード
```

`/upload` を取り込みの入口とし、`/` はダッシュボードとする。共通ヘッダーから「取り込む」「解析履歴」に進める。履歴へのリンクは対象の受付月を渡す。月をまたいで送信した場合も、今回の一覧は画像ごとの依頼IDで追う。

## 記号の凡例

`[ 操作 ]` はボタン、`リンク >` は遷移、`[ 値 v ]` は選択欄、`[画像]` はローカル画像のプレビュー。`○` 選択済み、`↑` 送信中、`…` 待機・解析中、`✓` 登録完了、`－` 登録対象なし、`!` 注意、`×` 失敗。記号には必ず日本語ラベルを添える。例の日時・ファイル名・件数はサンプル。

## スマートフォン: 選択前（360px / 390px）

```text
┌──────────────────────────────────┐
│ snap_kakeibo                     │
├──────────────────────────────────┤
│ レシートを取り込む               │
│ 撮影するか、画像を選んでください │
│                                  │
│ [ レシートを撮影 ]               │
│ [ 画像を選ぶ（複数可） ]         │
│                                  │
│ 1枚の画像につき1件ずつ解析します │
│ 日付と合計まで写してください。   │
│                                  │
│ 解析履歴を見る >                 │
└──────────────────────────────────┘
```

- `レシートを撮影` は背面カメラを優先する画像入力。端末が対応しない場合は標準のファイル選択に委ねる。カメラを開けなくても `画像を選ぶ` から進める。
- 撮影は1枚ずつ追加でき、画像選択は複数指定できる。選択をキャンセルしたら現在の内容を保つ。
- 選択直後には送信しない。ファイル形式・サイズの検証とプレビュー確認を経て、明示的に送信する。
- 対応形式・1枚あたりの上限・選択上限は実装時に画像処理の契約と揃え、選択操作の近くに記載する。現段階で未確定の数値や、PDF / HEIC 対応を案内しない。

## スマートフォン: 選択済み

```text
┌──────────────────────────────────┐
│ レシートを取り込む               │
│ [ 追加で撮影 ] [ 画像を追加 ]     │
│                                  │
│ 選択した画像  2枚                │
│ ──────────────────────────────── │
│ [画像] receipt-01.jpg             │
│        ○ 選択済み                │
│        [ 余白を切り取る ] [ 外す ] │
│ ──────────────────────────────── │
│ [画像] receipt-02.jpg             │
│        ○ 選択済み                │
│        [ 余白を切り取る ] [ 外す ] │
│ ──────────────────────────────── │
│ [ 2枚をアップロード ]            │
│                                  │
│ 解析履歴を見る >                 │
└──────────────────────────────────┘
```

プレビューは確定した送信画像の全体を表示し、見た目の都合で切り抜かない。タップすると拡大表示する。利用者が「余白を切り取る」で適用した場合だけ、画像そのものを切り抜く。ファイル名は折り返し、同名でも別の行として扱う。`外す` は未送信の選択を外すだけで、保存済み画像の削除ではない。全件を外したら選択前の状態に戻る。

形式・サイズが不適合な画像は行内に理由と `外す` を出す。有効な画像だけを対象に `N枚をアップロード` の件数を示し、不適合分は送信しないと明記する。有効な画像が0枚ならボタンを無効にし、送信できない理由を添える。

## 送信前のトリミング

- 有効な選択画像の各行に `余白を切り取る` を表示する。編集は画像ごとに独立し、送信済み画像は編集できない。
- ダイアログで元画像全体と縦横比を固定しない矩形枠を表示する。枠内のドラッグで移動、四隅のドラッグでサイズを変える。タッチ・マウスに対応する。
- 枠内と四隅はTabで移動でき、矢印キーで画像寸法の0.5%、Shift併用で5%ずつ調整できる。Enter/Spaceで各操作ボタンを実行できる。ダイアログ内にフォーカスを留め、Escapeはキャンセルし、閉じたら操作元へフォーカスを戻す。
- 初回にブラウザ内で範囲候補を検出する。検出中も手動操作・キャンセルできる。利用者が枠を動かした後に届いた検出結果は反映しない。自動では適用しない。
- 候補なし、曖昧な複数候補、境界の欠け、検出失敗・5秒超過では画像全体から手動調整できる。店名・商品・日付・合計が含まれるか利用者に確認を促す。
- `適用` は元解像度の元画像から切り抜いて選択一覧へ戻る。EXIFの向きを反映した表示と同じ座標を使い、検出用縮小画像を送信しない。JPEGは品質0.95、PNGはPNGで出力し、形式と29 MiB以下の条件を再検証する。失敗時はダイアログに理由を示し確定画像を維持する。
- `キャンセル` / Escape は今回の編集を破棄し、直前に確定した画像を維持する。`元に戻す` は編集中の枠を画像全体へ戻す。`切り取らずに使う` は元Fileを選択画像として確定する。全体のまま `適用` した場合も元Fileを使う。
- 切り取り後は `切り取り済み` を表示し、サムネイル・拡大・一括送信・送信先作成失敗時の再試行で同じ確定Fileを使う。再編集は元画像から行い、再圧縮を繰り返さない。
- サーバーに保存され、後から表示・再解析されるのは確定した送信画像。切り取り前画像は送信前の編集用に端末内だけで保持し、二重保存しない。送信開始、除外、差し替え、画面離脱時に不要なURL・元画像参照を解放する。
- 自動検出は追加ライブラリ・AIモデルなし。専用Workerで長辺480px以下の画像から明度・色の連続領域、輪郭のコントラスト、面積・矩形充填率を評価し、各辺に画像寸法の3%の余白を付ける。白色・縦横比だけでは判定しない。台形・湾曲補正、複数レシート分割は対象外。
- 評価方法・検出失敗例・読み取りの比較は [トリミング評価](../../receipt-cropping-evaluation.md) を参照する。自動提案や文字の読取改善を保証しない。

## スマートフォン: 送信後・結果が混在

```text
┌──────────────────────────────────┐
│ レシートを取り込む               │
│ [ 追加で撮影 ] [ 画像を追加 ]     │
│                                  │
│ 今回の取り込み  4枚              │
│ 登録完了1 / 進行中2 / 要対応1    │
│ 状態確認 12:04                   │
│ [ 再読み込み ]                   │
│                                  │
│ [画像] receipt-01.jpg             │
│        ✓ 登録完了                │
│        支出詳細を見る >          │
│ ──────────────────────────────── │
│ [画像] receipt-02.jpg             │
│        … 解析中                  │
│        結果は再読み込みで確認    │
│ ──────────────────────────────── │
│ [画像] receipt-03.jpg             │
│        ↑ アップロード中          │
│        送信が終わるまで          │
│        この画面を開いてください │
│ ──────────────────────────────── │
│ [画像] receipt-04.jpg             │
│        × 解析失敗                │
│        合計金額を読み取れません  │
│        でした。                  │
│        [ 再解析する ]            │
│        撮り直してアップロード > │
│ ──────────────────────────────── │
│ 解析履歴を見る >                 │
└──────────────────────────────────┘
```

- 図の追加操作は送信処理中は無効にする。送信が終われば、解析を待ちながら次の画像を追加できる。未送信分は「選択した画像」、送信開始済みは「今回の取り込み」に分け、未送信分を上に置く。
- 一括送信は画像単位に進め、1枚の失敗で他を止めない。順番は選択順のまま保ち、完了順への並べ替えや詳細への自動遷移はしない。
- 件数の内訳は、登録完了・進行中・登録対象なし・要対応（失敗／期限切れ／停滞）のうち0件以外を表示する。選択中の未送信分は含めない。
- POST成功後、サーバーがまだ `UPLOADING` なら「送信済み・解析開始待ち」と表示する。サーバーが `ANALYZING` になってから「解析中」とする。
- 全POSTの成功が確認できたら「画像の送信が終わりました。画面を離れても解析は続きます。結果は解析履歴から確認できます」と案内する。解析完了とは表示しない。
- 全件が終端でも `登録対象なし` や失敗をまとめて「成功」にしない。登録完了には常に支出詳細リンクを残す。

## PC: 取り込み状況（1280px）

最大幅1120pxの1カラム。撮影・選択の操作を横並びにし、画像ごとの情報は罫線で区切った行にする。広さを埋めるためのカードや右側の支出編集パネルは置かない。

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ snap_kakeibo                                                             │
├──────────────────────────────────────────────────────────────────────────┤
│ レシートを取り込む                                  解析履歴を見る >    │
│ [ レシートを撮影 ] [ 画像を選ぶ（複数可） ]                               │
│                                                                          │
│ 今回の取り込み 3枚    登録完了1 / 進行中1 / 要対応1                       │
│ 状態確認 12:04                                        [ 再読み込み ]      │
│ ──────────────────────────────────────────────────────────────────────── │
│ 画像・ファイル名             状態                    次の操作             │
│ [画像] receipt-01.jpg        ✓ 登録完了              支出詳細を見る >     │
│ ──────────────────────────────────────────────────────────────────────── │
│ [画像] receipt-02.jpg        … 解析中                再読み込みで確認     │
│ ──────────────────────────────────────────────────────────────────────── │
│ [画像] receipt-03.jpg        ! 期限切れ              [ 再アップロード ]   │
│                             送信期限を過ぎました                         │
└──────────────────────────────────────────────────────────────────────────┘
```

## 状態と回復操作

サーバー状態の判定・エラー文言は [解析履歴の状態表](../analysis-requests/README.md#ステータス表示) と共通にする。

| 場面 | 表示・次の操作 |
| --- | --- |
| 送信開始前 | `選択済み`。追加・除外・送信ができる |
| アップロード先作成中 / POST中 | `アップロード中`。送信ボタンは無効、画像の追加・除外も停止。解析状況の再読み込みは可能 |
| アップロード先作成失敗 | 選択を保持して「送信を開始できませんでした」。対象画像だけ `再試行` |
| POST失敗 | 「画像を送信できませんでした」。依頼IDが分かる場合はまず `状態を確認` で最新状態を確認し、送信済みなら重ねて送らない |
| 期限切れ | 「送信期限を過ぎました」。`再アップロード` で新しい依頼を作る |
| 停滞 | 「解析に時間がかかっています」。`再解析する` と `再読み込み` |
| 登録完了 | `支出詳細を見る`。完了は登録済みの意味で、利用者による確認済みという意味ではない |
| 登録対象なし | 「登録できる明細が見つかりませんでした。家計簿には反映されていません」。`再解析する` と撮り直すリンク |
| 解析失敗 | 理由と回復操作を併記。`TOO_MANY_DETAILS` では再解析を出さず、画像を見直して再アップロードする案内 |
| 状態取得失敗 | 最後に確認できた行を残し「最新の状態を取得できませんでした」。送信失敗へ変更せず `再読み込み` |

### 行内の表示例

エラーだけの別画面にはせず、状態に応じて同じ行を差し替える。

```text
! 期限切れ                     ! 停滞
送信期限を過ぎました。         解析に時間がかかっています。
[ 再アップロード ]             [ 再解析する ]
                               再読み込みで最新状態を確認

－ 登録対象なし                × 画像を送信できませんでした
登録できる明細が               送信結果を確認してください。
見つかりませんでした。         [ 状態を確認 ]
家計簿には反映されていません。
[ 再解析する ]
撮り直す >
```

再解析は確認ダイアログに対象ファイル名と「保存済みの画像でもう一度読み取りを行います」を表示し、`キャンセル` / `再解析する` を置く。受付成功は「解析中」であり、登録完了ではない。

再解析の確認・結果・失敗は [解析履歴の回復操作](../analysis-requests/README.md#回復操作) と共通にする。

再アップロードは新しい依頼として登録する。同一セッションで元の画像を保持していればその画像を再選択済みにできる。保持していなければ `/upload` で撮影・選択を促す。元の失敗行は履歴に残り、置き換えや削除とはしない。通信結果が不明なままの再送は重複登録の可能性を説明し、先に状態確認を案内する。

## 後から確認する解析履歴

```text
┌────────────────────────────────┐
│ 解析履歴                       │
│ [ レシートを取り込む ]         │
│                                │
│ ┌────────────────────────────┐ │
│ │検索条件                    │ │
│ │受付月 [ 2026年9月 v ]     │ │
│ │購入月とは異なります。      │ │
│ │表示 [ 要対応 v ]          │ │
│ │要対応を見る >              │ │
│ └────────────────────────────┘ │
│                                │
│ ┌────────────────────────────┐ │
│ │履歴  2026年9月 / 要対応    │ │
│ │状態確認 12:04              │ │
│ │[ 再読み込み ]              │ │
│ │────────────────────────────│ │
│ │9/22 12:00  × 解析失敗     │ │
│ │receipt-04.jpg              │ │
│ │合計金額を読み取れません    │ │
│ │でした。                    │ │
│ │[ 再解析する ]              │ │
│ │撮り直してアップロード >   │ │
│ │────────────────────────────│ │
│ │9/22 10:30  ! 停滞         │ │
│ │receipt-01.jpg              │ │
│ │[ 再解析する ]              │ │
│ │────────────────────────────│ │
│ │[ 前へ ] 1ページ目 [ 次へ ] │ │
│ └────────────────────────────┘ │
└────────────────────────────────┘
```

検索条件と履歴をそれぞれ1つのカードにまとめ、画像単位では罫線で区切る。履歴の月・絞り込み・ページ・位置は詳細から戻る際に保持する。絞り込みは表示中のページだけでなく受付月全体に適用する。

登録完了行には支出詳細リンクを置く。店舗名・計上額はAPI対応後に追加し、対応前は架空の値を出さない。履歴には画像URLがないため、ファイル名と受付日時で対象を識別する。

| 一覧の状態 | 履歴カード内の表示 |
| --- | --- |
| 初回取得中 | 「解析履歴を読み込み中」 |
| その月に履歴がない | 「この受付月の取り込みはありません」と取り込みリンク |
| 要対応がない | 「要対応の画像はありません」と `すべてを見る` |
| 初回取得失敗 | 「解析履歴を読み込めませんでした」と `再読み込み` |
| 再取得中 | 前の一覧を残して `再読み込み中…` |
| 再取得失敗 | 前の一覧・確認時刻と、取得失敗の案内 |

PCでは検索条件カードの月・状態を横並びにし、履歴カードは受付日時／ファイル名／状態・理由／操作の表にする。行内の操作を隠さず、行全体のクリックとボタンクリックを競合させない。詳細は [解析履歴の仕様](../analysis-requests/README.md) を参照。

## 画面を離れるとき

- 未送信の選択やPOST処理がある場合、アプリ内の遷移（完了行の詳細リンクも含む）には「未送信の画像があります。移動すると送信が中断されることがあります」と `この画面に戻る` / `移動する` を出す。ページ再読み込み・タブを閉じる場合はブラウザー標準の離脱確認を使う。
- POST完了後の解析待ちだけなら離脱確認を出さない。アップロード再開を保証せず、後から解析履歴で確認する。
- アプリ内で支出詳細へ移動して戻った場合は、今回の依頼ID・行の位置・ローカルプレビューを保持する。ページ再読み込み後の画像File復元は保証しない。
- サーバー側に依頼がある画像は解析履歴から再発見できる。未送信の選択は履歴に出ない。

## 表示とアクセシビリティ

- 状態は記号と日本語を併記し、緑は主要操作・完了、橙は注意、赤は失敗に使う。装飾用のカード・指標・画像・グラデーションは追加しない。
- 本文16px、補助14px、左右余白16px（PCは24px）、行間1.6。操作は44px以上、角丸・区切り線・状態色は共通トークンを使う。
- 360px / 390pxではファイル名・状態・操作を縦に並べる。768pxも1カラム、960px以上で行内を横並びにする。ボタンは折り返し、固定フッターで下の画像を覆わない。
- 撮影・選択・送信を順にたどれるキーボード操作とフォーカス表示を提供する。拡大画像はダイアログにし、Escで閉じて操作元へ戻る。
- ファイル入力にラベルを付ける。`外す` や再試行には対象ファイル名を読み上げ名に含める。行のエラーは該当画像と関連付ける。
- 状態確認時刻は取得成功時だけ更新する。取得失敗時は一覧の上に案内を置き、直前の状態と確認時刻を保つ。
- 再取得中は内容を保ち `再読み込み中…`。再読み込み後3秒は連打を防ぐ。状態変化は `aria-live="polite"` で要約し、勝手にフォーカスを移動しない。
- 初回の状態取得は共通の読み込み表示。スピナーは `prefers-reduced-motion` で静止し、解析待ちに動き続ける演出を置かない。

## API設計

### POST /uploads

1画像のアップロード先を作成する。画面上の一括送信では画像ごとにこのAPIを呼び、1枚の失敗で他を止めない。

Request:

```json
{
  "file_name": "receipt-1.jpg",
  "content_type": "image/jpeg"
}
```

Response:

```json
{
  "analysis_request_id": "01JREQUESTXXX",
  "s3_key": "receipts/01JUSERXXX/01JREQUESTXXX/original.jpg",
  "post_url": "https://example.com/presigned-post",
  "post_fields": {"key": "receipts/01JUSERXXX/01JREQUESTXXX/original.jpg", "Content-Type": "image/jpeg", "policy": "...", "X-Amz-Signature": "..."},
  "expires_at": "2026-09-15T12:15:00Z"
}
```

`post_fields` は S3 にそのまま送る署名済みフォーム項目。`file` を最後に追加して multipart/form-data で送信する。ポリシーは multipart 全体を 30 MiB 以下に制限し、画面ではフォームの余裕を見て画像を 29 MiB 以下に制限する。`expires_at` は署名済みフォームの有効期限。期限内にPOSTできなかった画像は「失敗」として表示し、再アップロードを促す。

## 実装との対応・未確定事項

`UploadPage` は現行の単一ファイルAPIを画像ごとに並行して呼び、複数選択・撮影・今回の一覧を実装する。作成済み依頼IDと月一覧APIの結果を照合して、送信後のサーバー状態を表示する。

- 対応形式は、バックエンドの画像デコード契約に合わせて JPEG / PNG とする。画像は 29 MiB 以下に制限し、超える場合は選択一覧に理由を表示して送信対象から外す。
- 受付月は購入月とは別。月境界で今回の依頼を見失わないよう、APIの月の算出規則と受付日時の取得方法を実装時に確認する。
- 枚数上限とアップロード応答喪失時の重複防止は別課題とする。
- 履歴のページネーション・月全体の絞り込み・店舗名と計上額の取得にはAPI対応が必要。[解析履歴の未対応項目](../analysis-requests/README.md#画面設計に対して未対応の項目) に従う。
- 旧 `ReceiptIntakePage` の送信・依頼一覧・支出表示は、アップロード画面、解析履歴画面、支出詳細画面に分離済み。状態判定・回復操作・再読み込みは画面間で共通化する。

## 設計レビュー項目

- 撮影→追加選択→1枚除外→送信→再読み込み→詳細→戻る、の一連の操作ができる。
- 主要操作の優先順位、余白、文字の階層、確定画像全体の表示、状態と操作の隣接を確認する。
- 1枚だけPOST失敗しても他の解析が進み、完了行から支出詳細へ移動できる。
- 送信中の離脱と、解析待ちでの離脱の扱いが異なる。
- 期限切れ・停滞・登録対象なし・解析失敗にそれぞれ次の操作がある。
- 詳細から戻って対象画像を見失わず、再読み込み後も解析履歴からたどれる。
- 色だけに依存せず、長いファイル名、360pxでの操作の折り返し、フォーカス、拡大の復帰を実装時に確認する。

- 切り取りの適用・キャンセル・全体への復帰、画像ごとの独立性、プレビューと実送信の一致、再試行、EXIFの向き、検出中の手動調整・キャンセル、出力中のキャンセルを確認する。

## 静的モック

[操作できるアップロード画面モック](./mock.html) で、初期の空状態、画像の選択確認と除外、疑似アップロード、画像ごとの状態、手動再読み込み、再解析・送信状態の確認、画像プレビューを確認できる。端末内の画像も選択できるが、表示に使うだけで外部へ送信しない。モック内の操作は実API、画像保存、家計簿データの更新を行わない。

「モックの表示状態を切り替える」から、結果が混在した状態と期限切れ・停滞などの回復操作も直接表示できる。[解析履歴モック](../analysis-requests/mock.html) との間を移動でき、`?file=ファイル名` 付きで開くと撮り直し対象の案内を表示する。

静的モックはブラウザーで360px / 390px / 768px / 1280pxの画面幅と主要操作を確認済み。実APIを使った操作はUI実装時に検証する。

リポジトリルートで `python3 -m http.server 4176 --directory docs/screens` を実行し、`http://localhost:4176/upload/mock.html` を開く。まず「サンプル画像を追加」から画像なしでも操作できる。

モックでは支出詳細の共通サンプルを別タブで開く。選択画像ごとの支出データ連携、解析履歴との状態共有、ページ再読み込み後の復元、離脱確認、形式・容量の検証は未実装。撮影は端末のファイル入力に委ね、実機カメラの動作は未検証。混在サンプルの「アップロード中」は表示確認用に固定している。

Playwrightで360px / 390px / 768px / 1280pxの横あふれと選択・除外・疑似送信・プレビュー・再解析・再読み込み・回復操作を確認した。文字階層、余白、状態色とラベル、画像の表示、長いファイル名の折り返しはスクリーンショットでも確認した。

静的モックはトリミングに未対応。トリミングは `front/` の実装で確認する。
